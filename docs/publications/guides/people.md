# Как пользоваться фабрикой ПО на ИИ

Собрано из модели и файлов фабрики, версия источника 48de3911fc79. Правка - в источнике, не здесь.

## Коротко

Фабрика ПО на ИИ - координирует работу, исполняет задачи агентами, проверяет результат стражами правил и управлением, ведёт базу знаний.

Я бот фабрики. Спросите меня (упоминанием) о проекте - отвечу со ссылками на правила, решения и задачи.

## Подготовка

1. Стенд фабрики поднят (`scripts/stand-up.sh`), экземпляр демо - `scripts/demo-up.sh`.
2. Проверить, что всё на связи: в Discord `!дейли` - ответ бота; стенд цели http://127.0.0.1:8082 открывается; GlitchTip http://127.0.0.1:8200.
3. У разработчиков подключён MCP фабрики (`http://127.0.0.1:4100/mcp`, ключ - `.state/coordinator/mcp.token`): BE - в Claude Code, FE - в Codex.
4. Решить, что делать со следами наладки: PR агентов 1, 2, 4, 8 и задачи DRAW-1..8 (слить, закрыть или оставить как прошлую работу команды).
5. Реестр ролей цели (`.factory/roles.yml`): учётки участников прогона (Discord, Atlassian, ключ MCP) внесены, роли розданы. Команды в точках решения - из своей учётки Discord: вебхук получит отказ.

## По ролям

### Product Owner

Product Owner задаёт вопросы фабрике в Discord `#продукт`. Product Owner заводит стори в Confluence или Jira, а сверщик сверяет её со знанием проекта.

**Как спросить о знании проекта**

1. В Discord `#продукт` напишите `@Factory` и вопрос, например `@Factory что известно про невостребованные призы?`.
2. Прочитайте ответ библиотекаря со ссылками на источники.

**Как завести стори**

1. Создайте в Confluence страницу-стори с меткой `story` или задачу Jira с той же меткой.
2. Подождите одну-две минуты: поиск Confluence отстаёт от записи.
3. Найдите стори в Jira и комментарий сверщика с цитатами и ссылками.
4. Проверьте, есть ли у стори метка `needs-decision`: тогда стори зависит от задачи на решение с меткой `decision`.
5. После закрытия задачи на решение дождитесь у стори метки `story-ok` и сообщения в `#продукт`.

Основания: шаг 1, шаг 2, модель (factory.reconciler), шаг 3.

### Архитектор

Архитектор снимает противоречия стори с решениями проекта: уточняет ADR и добавляет правила-стражи. Архитектор решает по PR-кандидату с новым правилом.

**Как снять противоречие в стори**

1. Откройте PR в prize-draw с уточнением ADR.
2. Добавьте в тот же PR правило-страж в `.factory/config.yml`: `forbid`, `paths` и сообщение со ссылкой на ADR.
3. Слейте PR и закройте задачу на решение.
4. Найдите у стори комментарий сверщика "противоречие снято решением ..." и метку `story-ok`.

**Как принять правило-кандидат**

1. Откройте PR-кандидат со строкой в `AGENTS.md` и правилом-стражем.
2. Решите по нему: вердикт в PR-кандидате - "решает архитектор".
3. После слияния проверьте, что страж применяет правило.

Основания: шаг 3, шаг 11.

### Project Manager

Project Manager нарезает стори на задачи и передаёт баги агенту. Project Manager смотрит сводку работы фабрики и учёт работы агентов.

**Как нарезать стори на задачи**

1. В Discord напишите `!нарезка DRAW-N` по согласованной стори.
2. Проверьте предложенные задачи.
3. Напишите `!утвердить DRAW-N`, чтобы завести задачи.
4. Проверьте, что задачи заведены по одному шаблону (цель, сценарии приёмки "Дано, Когда, Тогда", вне рамок, основания) и связаны со стори.

**Как передать баг агенту**

1. В Jira поставьте на баг метку `agent`.
2. Дождитесь PR агента с исправлением.
3. После слияния и выкладки проверьте, что баг и ошибка в GlitchTip закрылись.

**Как узнать, что делает фабрика**

1. Напишите в Discord `!дейли`, чтобы увидеть задачи агентов, PR, решения и выкладку.
2. Напишите `!учёт`, чтобы увидеть попытки, время и цену работы агентов по задачам.

Основания: шаг 4, шаг 10, шаг 14, !нарезка, !дейли, !учёт.

### Разработчик BE

Разработчик BE готовит спецификацию изменения в Claude Code и передаёт задачу API агенту. Разработчик BE делает ревью PR агента в Claude Code с MCP фабрики.

**Как подключить MCP фабрики**

1. Подключите в Claude Code MCP фабрики по адресу `http://127.0.0.1:4100/mcp` с ключом из `.state/coordinator/mcp.token`.

**Как отдать задачу API агенту**

1. В Claude Code с навыками OpenSpec выполните `/opsx:propose` по задаче API.
2. Проверьте изменение командой `npm run spec:validate` и откройте PR.
3. После слияния PR владельцем поставьте метку `agent` на задачу API.
4. Найдите в задаче комментарий "Фабрика взяла задачу" и метку `agent-running`.

**Как проверить стража на PR агента**

1. Добавьте в PR агента коммит с `Math.random()` в `api/src/`.
2. Убедитесь, что вердикт красный и называет правило no-random-outside-seed (ADR-3) с местом нарушения.

Основания: шаг 4a, шаг 7, подготовка 3.

### Дизайнер

Дизайнер сверяет макет экрана с задачей через Discord.

**Как сверить макет**

1. В Discord напишите `!макет DRAW-N` со ссылкой на рамку Figma или приложите картинку PNG экрана.
2. Найдите в задаче комментарий судьи макета.
3. Проверьте метку задачи: `design-ok` или `design-changes`.

Основания: шаг 5a, !макет.

### Разработчик FE

Разработчик FE работает в Codex с MCP фабрики. На PR разработчика FE фабрика ставит те же проверки, что и на PR агента.

**Как подключить MCP фабрики**

1. Подключите в Codex MCP фабрики по адресу `http://127.0.0.1:4100/mcp` с ключом из `.state/coordinator/mcp.token`.

**Как сделать экран по правилам фабрики**

1. Вызовите `factory_rules`, чтобы узнать, что фабрика проверит у изменения.
2. Ищите правила и решения проекта через `kb_search`.
3. Сделайте экран и откройте PR.
4. Проверьте на PR статусы `factory/verdict`, `factory/scan` и комментарий стража.

Основания: подготовка 3, шаг 6, factory_rules, kb_search.

### QA

QA перезапускает CI и сквозные проверки цели из Discord.

**Как перезапустить CI**

1. Напишите в Discord `!ci N`, где N - номер PR.
2. Чтобы перезапустить CI ветки по умолчанию, напишите `!ci` без номера.
3. Прочитайте итог новой попытки CI в канале.

**Как перезапустить сквозные проверки**

1. После выкладки напишите `!e2e`.
2. Прочитайте итог в том же канале.

Основания: шаг 7a, !ci, !e2e.

### Владелец области

Владелец области сливает PR, и служба выкладки выкладывает коммит на стенд.

**Как выложить изменение на стенд**

1. Слейте PR.
2. Проверьте статус `factory/deploy` "выложено на стенд (main)".
3. Найдите в задаче агента комментарий со ссылками на коммит, PR и выкладку.
4. Найдите сообщение в `#разработка`.

Основания: шаг 8.

### Эксплуатация

Эксплуатация получает баги о сбоях стенда в Jira и сообщения в Discord `#эксплуатация`.

**Как проверить, что сбой становится багом**

1. Пока PR 8 не слит, вызовите сбой на стенде заявкой с датой рождения `2000-13-45`.
2. Найдите в Jira баг с меткой отпечатка и ссылкой на событие GlitchTip.
3. Найдите сообщение в `#эксплуатация`.
4. Повторите сбой и проверьте, что в баг пришёл комментарий, а второй баг не появился.

Основания: шаг 9, модель (factory.cd).

### Ревьюер

Ревьюер оставляет замечания к PR в GitHub. По команде `!правила` сверщик ищет повторяющиеся замечания и предлагает правило.

**Как превратить повторяющееся замечание в правило**

1. Оставьте одно и то же замечание в трёх PR, например "срок подтверждения без часового пояса".
2. Напишите в Discord `!правила`.
3. Найдите PR-кандидат со строкой в `AGENTS.md` и правилом-стражем.
4. Найдите сообщение в `#разработка`.

Основания: шаг 11, !правила.

### Релиз-менеджер

Релиз-менеджер смотрит состав выпуска и ставит тег, по которому фабрика готовит черновик заметок о выпуске. Подтвердить выкладку могут роли devops и release-manager.

**Как подготовить выпуск**

1. В Discord `#релизы` напишите `!выпуск`, чтобы увидеть, что войдёт в следующий выпуск.
2. Поставьте тег выпуска в prize-draw, например `v1.1.0`.
3. Проверьте черновик заметок о выпуске: изменения с прошлого тега, PR, задачи.

Основания: шаг 12, !выпуск, шаг 12a.

### DevOps

DevOps подтверждает выкладку выпуска на стенд из Discord `#релизы`.

**Как выложить выпуск на стенд**

1. Пишите команду из своей учётки Discord: сообщение вебхука получит отказ.
2. В `#релизы` напишите `!выкладка v1.1.0`.
3. Проверьте, что стенд перешёл на образы v1.1.0.
4. Проверьте, что задачи выпуска получили метку `release-v1.1.0`.
5. Найдите страницу "Выпуск v1.1.0" в Confluence.
6. Найдите сообщение в `#релизы`.

Основания: шаг 13, !выкладка, подготовка 5, шаг 12a.

## Справочник

### Команды бота в чате

| Команда | Что делает |
|---|---|
| `!дейли` | что делает фабрика: задачи агентов, PR, решения, выкладка |
| `!задача <название>. <описание>` | задача агенту фабрики |
| `!выпуск` | что войдёт в следующий выпуск |
| `!выкладка vX.Y.Z` | подтвердить выкладку выпуска на стенд |
| `!учёт` | попытки, время и цена работы агентов по задачам |
| `!правила` | сверщик ищет повторяющиеся замечания к PR и предлагает правило |
| `!нарезка DRAW-N` | предложить задачи по стори; !утвердить DRAW-N [agent] - завести их |
| `!e2e` | перезапустить сквозные проверки цели на стенде; итог - сюда же |
| `!ci [номер PR]` | перезапустить CI цели (GitHub Actions) для PR или ветки по умолчанию |
| `!судья N` | судья фабрики (Codex) снова смотрит PR N |
| `!макет DRAW-N [ссылка на рамку Figma]` | сверить макет с задачей (или приложите картинку PNG) |

### Инструменты MCP фабрики

| Инструмент | Что даёт |
|---|---|
| `kb_search` | Поиск по знанию проекта - отрывки правил, решений (ADR) и описаний проекта со ссылками на источник в git. |
| `check_requirement` | Сверка требования со знанием проекта - сверщик фабрики: противоречит ли требование правилам и решениям проекта; с цитатами и ссылками. |
| `factory_rules` | Правила стражей фабрики - что проверит фабрика у любого изменения: правила для агентов цели, команды проверок и пределы стража. |
| `submit_task` | Передать задачу агенту фабрики - заводит задачу в трекере с меткой агента: фабрика сама отдаст её агенту и откроет PR. |

### Точки решения ролей

Кто их принимает, задаёт реестр ролей цели `.factory/roles.yml`.

- deploy - подтвердить выкладку
- approve-slice - утвердить нарезку
- slice - предложить нарезку
- submit-task - передать задачу агенту
- story - отдать стори на сверку
- propose-rule - предложить правило
- rerun-checks - перезапустить проверки
- design-check - сверить макет
