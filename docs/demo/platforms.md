# Платформы демо: учётки и токены

Стадия 2 из [architecture.md](architecture.md). Токены живут только в `.state/` (каталог не попадает в git), права на файлы - 600. В чат и в аргументы команд токены не попадают. Сроки жизни токенов - не больше года; напоминание о продлении - в календаре.

Создать пустой файл с правильными правами и открыть его в редакторе:

```sh
install -m 600 /dev/null .state/atlassian.env
```

## Jira и Confluence

1. Создать проект Jira "Розыгрыш призов" с ключом `DRAW` (шаблон Scrum) и пространство Confluence с ключом `DRAW`.
2. На https://id.atlassian.com/manage-profile/security/api-tokens выбрать "Create API token with scopes" - два токена, по одному на продукт (у токена с областями один продукт):
   - `factory-jira`: продукт Jira; области `read:jira-work`, `write:jira-work`, `read:jira-user`;
   - `factory-confluence`: продукт Confluence; области `read:confluence-content.all`, `read:confluence-space.summary`, `write:confluence-content`, `search:confluence`.
   Токен с областями ходит через `api.atlassian.com` по идентификатору сайта (cloudId); фабрика узнаёт его сама.
3. `.state/atlassian.env`:

```sh
ATLASSIAN_SITE=https://<сайт>.atlassian.net
ATLASSIAN_EMAIL=<почта учётки>
JIRA_API_TOKEN=<factory-jira>
CONFLUENCE_API_TOKEN=<factory-confluence>
JIRA_PROJECT=DRAW
CONFLUENCE_SPACE=DRAW
```

## Bitbucket (платформа фабрики)

1. В рабочем пространстве создать репозиторий `factory` (можно закрытый) и включить Pipelines: Repository settings -> Pipelines -> Settings -> Enable Pipelines.
2. Токен репозитория: Repository settings -> Security -> Access tokens -> Create. Имя `factory-coordinator`, права: Repositories - Read, Write; Pull requests - Read; Pipelines - Read, Write, Edit variables; Runners - Read. Если пункта Access tokens нет, взять API-токен с областями для Bitbucket на id.atlassian.com (`read:repository:bitbucket`, `write:repository:bitbucket`, `read:pipeline:bitbucket`, `write:pipeline:bitbucket`, `read:runner:bitbucket`). Пароли приложений Bitbucket выведены из работы.
3. Свой раннер: Repository settings -> Pipelines -> Runners -> Add runner -> Linux Docker (x86_64), имя `laptop`, метка `factory`. Показанную команду **не запускать**: она даёт раннеру Docker хоста. Из неё переписать значения в `.state/bitbucket-runner.env`; фабрика запустит раннер в отдельном Docker заданий.
4. Файлы:

```sh
# .state/bitbucket.env
BITBUCKET_WORKSPACE=<рабочее пространство>
BITBUCKET_REPO=factory
BITBUCKET_TOKEN=<factory-coordinator>

# .state/bitbucket-runner.env - значения из команды добавления раннера
ACCOUNT_UUID={...}
REPOSITORY_UUID={...}
RUNNER_UUID={...}
OAUTH_CLIENT_ID=...
OAUTH_CLIENT_SECRET=...
```

Запуск раннера на стенде и проверка (сделано 14.10.2026, пустой шаг `hello` прошёл за 7 с):

```sh
docker compose --profile bitbucket up -d          # bb-dind, bb-registry, bb-runner
scripts/bb-images.sh docker.io/library/alpine:3.24  # образы шагов - в свой реестр
scripts/bb-commit.sh "сообщение" ФАЙЛ bitbucket-pipelines.yml
scripts/bb-api.sh POST /pipelines/ ТЕЛО.json        # запуск задания
```

Устройство: шаги идут в отдельном Docker (`bb-dind`) во внутренней сети `bb-jobs`, наружу - только через прокси egress по адресу 172.31.250.10 (в allowlist - домены Bitbucket и Atlassian и реестр служебных образов раннера). Раннер всегда скачивает образ шага, поэтому образы шагов лежат в своём реестре `172.31.250.20:5000`. Рабочий каталог раннера - `/bb-work`, не под `/tmp`: скрипт dind монтирует на `/tmp` свой tmpfs. Сам раннер ещё и в сети фабрики: его клиент входа ходит на auth.atlassian.com мимо прокси.

## GitHub (платформа цели)

Репозиторий цели: https://github.com/ypolosov/prize-draw, открытый - Actions без лимита минут, образы GHCR открытые, выкладке не нужен токен реестра.

Два токена (fine-grained) на https://github.com/settings/personal-access-tokens/new, владелец `ypolosov`, срок 90 дней, Repository access - Only select repositories - `prize-draw`:

- `factory-read` - для шагов агента: Contents, Pull requests, Commit statuses, Actions - Read-only;
- `factory-publish` - для шага публикации: Contents, Pull requests, Commit statuses - Read and write; Actions - Read-only. Workflows - **No access**: фабрика не может менять CI цели, это делают только люди.

```sh
# .state/github-target.env
GITHUB_TARGET_REPO=ypolosov/prize-draw
GITHUB_READ_TOKEN=<factory-read>
GITHUB_PUBLISH_TOKEN=<factory-publish>
```

## Discord

1. Сервер команды с каналами `#продукт`, `#разработка`, `#эксплуатация`, `#релизы`, `#розыгрыши`.
2. User Settings -> Advanced -> Developer Mode; правый клик по серверу -> Copy Server ID.
3. https://discord.com/developers/applications -> New Application `Factory`:
   - General Information -> Application ID;
   - Bot -> Reset Token -> скопировать токен; Public Bot - выключить; Privileged Gateway Intents - включить Message Content Intent (библиотекарь читает каналы для базы знаний).
4. OAuth2 -> URL Generator: scopes `bot` и `applications.commands`; права бота - View Channels, Send Messages, Send Messages in Threads, Read Message History, Embed Links, Attach Files. Открыть ссылку, выбрать сервер, Authorize.
5. Вебхук приложения (объявление победителей): канал `#розыгрыши` -> Edit Channel -> Integrations -> Webhooks -> New Webhook -> Copy Webhook URL.

```sh
# .state/discord.env
DISCORD_APPLICATION_ID=...
DISCORD_BOT_TOKEN=...
DISCORD_GUILD_ID=...
DISCORD_DRAW_WEBHOOK_URL=...
```

## Figma (шаг дизайнера)

Бесплатного плана хватит, если не гонять API: чтение файла бесплатной команды через REST - до 6-20 запросов в месяц на основные методы, MCP Figma - 20 вызовов в месяц. Поэтому макет выгружается картинкой один раз на версию, и сверка идёт с картинкой. Лимиты считаются по команде, которой принадлежит файл.

Токен: Figma -> Settings -> Security -> Personal access tokens -> Generate new token, срок 90 дней, область File content - Read-only.

```sh
# .state/figma.env
FIGMA_TOKEN=...
FIGMA_FILE_KEY=<из адреса figma.com/design/<KEY>/...>
```

## Координатор: задача Jira -> PR

Сквозной путь демо (стадия 3): задача DRAW с меткой `agent` -> координатор на Mastra core -> задание `agent-task` на своём раннере Bitbucket -> агент по подписке -> PR в `prize-draw` со статусом стража `factory/verdict`.

```sh
scripts/demo-up.sh             # учётки, образ агента в реестр шагов, шлюз, координатор и выкладка цели
docker compose --profile bitbucket logs -f coordinator
```

- Метки задачи: `agent` - отдать агенту; `agent-running` - агент работает; `agent-review` - PR открыт, решает человек; `agent-failed` - агент или страж не дали результата (причина - в комментарии).
- Bitbucket получает только адрес посредника координатора (172.31.250.40:8080, сеть шагов) и разовый ключ запуска - скрытую переменную `RUN_TOKEN`. Задачу, рабочую копию цели (git bundle) и ключи подписки и шлюза шаг `factory-job` берёт у посредника, итог сдаёт туда же. Токены GitHub и вход подписки на Atlassian не уходят.
- Публикует координатор: ветка `agent/<запуск>`, PR, статус `factory/verdict`, комментарий с вердиктом. Шаг агента писать в цель не может: токенов записи у него нет, а GitHub не в allowlist прокси шагов.
- Страж до публикации: пустой патч, изменение `.github/`, `.factory/`, файлов CI и символические ссылки не публикуются; большой патч или сбой агента - PR с красным вердиктом.
- Страж требует от цели объявленных команд линтера и форматирования (`checks.lint`, `checks.format` в `.factory/config.yml`); файлы блокировки зависимостей в размер патча не входят.
- Выкладка цели (служба `cd`): CI цели после зелёных проверок публикует образы коммита main в GHCR, служба забирает их и `compose.yaml` этого коммита и поднимает систему в Docker выкладки стенда - http://127.0.0.1:8082; итог - статус `factory/deploy` на коммите.
- Сверка требований (UC1): задача DRAW с меткой `story` -> поиск по знанию цели (README, AGENTS.md, `docs/**/*.md`, спецификации OpenSpec `openspec/specs` и изменения в работе `openspec/changes` ветки по умолчанию; ссылки - на коммит) -> судья через шлюз (`kb-claude-cli`, подписка) -> противоречие: комментарий с цитатами и ссылками, задача на решение с меткой `decision` (стори зависит от неё), сообщение в Discord, метка `needs-decision`; закрытие задачи запускает повторную сверку с обновлённым знанием -> `story-ok` или "противоречие осталось". Без противоречий - сразу `story-ok`.
- Страж всех PR цели: PR из любого экзокортекса без вердикта фабрики на голове получает тот же `factory/verdict` и комментарий.
- MCP фабрики для экзокортексов (Claude Code, Codex): `http://127.0.0.1:4100/mcp`, инструменты `kb_search`, `check_requirement`, `factory_rules`, `submit_task`. Подключение Claude Code: `claude mcp add --transport http ai-factory http://127.0.0.1:4100/mcp --header "Authorization: Bearer $(cat .state/coordinator/mcp.token)"`.
- Бот фабрики в Discord (соединение исходящее, Gateway API): на упоминание отвечает библиотекарь - по знанию цели и задачам Jira, со ссылками; `!дейли` - задачи агентов, PR со вердиктами, решения и выкладка; `!задача Название. Описание` - задача агенту; уведомления сверщика - в `#продукт`.
- Выпуск (UC5): `!выпуск` в Discord - что войдёт в следующий выпуск (коммиты с прошлого тега, PR, задачи Jira). Тег `vX.Y.Z` в цели -> CI цели собирает образы выпуска -> координатор публикует черновик заметок в `#релизы` и ждёт подтверждения `!выкладка vX.Y.Z` (человек) -> проверяет образы в GHCR -> служба выкладки переходит на тег (общий том `cd-control`, файл `pin`) -> после статуса `factory/deploy` с тегом: задачи получают метку `release-vX.Y.Z` и комментарий, страница "Выпуск vX.Y.Z" в Confluence, сообщение в `#релизы`.
- Сбой на стенде (UC6): API цели шлёт необработанные ошибки в GlitchTip стенда (DSN - от службы выкладки, `.state/cd/app.env`; проект и токен координатора - `config/glitchtip/demo-setup.py`). Координатор опрашивает GlitchTip: новая ошибка -> баг в Jira (метки `bug`, `incident`, `incident-<id>` - без дублей) со ссылкой на событие и сообщение в `#эксплуатация`; повторы - комментариями; когда на стенд выложен коммит с ключом бага - баг закрывается, ошибка в GlitchTip тоже; повтор после исправления открывает баг снова.
- Учёт (`!учёт`): по каждой задаче агента - попытки, время агента и модели, теневая цена и токены из журнала шлюза (`.state/gateway-db`, по номеру запуска в `x-task-id`), PR и вердикт стража.
- Правила-стражи цели (UC7): раздел `rules` в `.factory/config.yml` цели - шаблон, запрещённый в добавленных строках файлов под `paths` (кроме `exclude`); нарушение даёт красный вердикт с объяснением у изменения агента и у любого PR. `!правила` - сверщик ищет замечание людей, повторённое минимум в трёх PR, и открывает PR-кандидат: строка в `AGENTS.md` и правило-страж; слияние архитектором - утверждение.
- Нарезка стори (UC2): `!нарезка DRAW-N` - сверщик предлагает 2-6 задач по стори и знанию проекта; `!утвердить DRAW-N` (или `... agent` - сразу агенту) - PM утверждает, задачи заводятся и связываются со стори. Пауза до утверждения переживает перезапуск.
- Судья PR (Codex по подписке, другое семейство моделей, чем агент): любой открытый PR с вердиктом стража получает статус `factory/judge` (оценка 0-100, рекомендация) и комментарий с главными замечаниями. Задание - на своём раннере через посредника; шаг получает только ключ шлюза подписок и вход Codex; обновлённый в шаге вход возвращается фабрике.
- e2e на стенде (`!e2e`, QA): сквозные проверки цели с коммита, что выложен на стенд, на своём раннере против стенда (Docker выкладки - в сети шагов, 172.31.250.50); итог - в канал запроса. Права на запуск Actions цели не нужны.
- Перезапуск CI цели (`!ci [номер PR]`): прогоны GitHub Actions головы PR или ветки по умолчанию перезапускаются; итог новой попытки - в канал запроса. Токену `factory-publish` нужно право Actions: Read and write.
- Стори из Confluence: страница пространства DRAW с меткой `story` -> стори в Jira (метки `story` и `wiki-<id>`, ссылка на страницу) -> сверщик; правка страницы обновляет стори и запускает сверку заново; итог сверки - комментарием на странице. Страницы Confluence - ещё и источник знания для сверщика и библиотекаря (поиск CQL). Индекс поиска Confluence отстаёт от записи до минуты.
- Сверка макета (UC3): `!макет DRAW-N` с картинкой PNG в сообщении или ссылкой на рамку Figma Design - судья макета (Codex по подписке, видит картинки) сверяет экран с задачей и правилами проекта; итог - комментарий в задаче, метка `design-ok` или `design-changes`, сообщение в канал. Файлы Figma Make REST API Figma не отдаёт (`File type not supported`): для них - картинка в сообщении. Ссылка на страницу, а не на рамку, - берётся первая рамка на странице. Бесплатный план Figma даёт мало запросов в месяц - одна сверка тратит один-два.
- Реестр ролей (`.factory/roles.yml` цели): держатели (человек, человек со своими ИИ-агентами, ИИ-агент), их учётки в инструментах, роли и точки решения с разрешёнными ролями. Фабрика проверяет права по роли учётки: команды бота `!выкладка`, `!утвердить`, `!нарезка`, `!задача`, `!правила`, `!e2e`, `!ci`, `!макет` и метки `agent` и `story` (кто поставил метку, а если она с создания - кто завёл задачу). Стори из вики - по автору текущей версии страницы, `submit_task` в MCP - по учётке, которую называет ключ (файл ключей MCP: строки `учётка ключ`, один ключ без имени - учётка `default`). Без нужной роли - отказ с объяснением, метка снимается. Вебхук чата может подписаться любым именем - его сообщения в точках решения не проходят. Метки от учётки самой фабрики второй раз не проверяются: их проверили там, где решение приняли (чат, MCP, вики, нарезка). Поэтому фабрике нужна своя учётка; в демо она ходит в Jira и Confluence учёткой владельца, и его метки в Jira считаются метками фабрики. Нет реестра - открытый режим, как раньше.
- Сканеры изменения: каждая новая голова PR цели (агента и человека) получает статус `factory/scan` - секреты в добавленных строках (Gitleaks), новые уязвимости зависимостей (OSV-Scanner по файлам блокировки на общем предке и на голове; база OSV скачивается в шаге - API OSV отсюда закрыт, около 3 минут) и лицензии новых пакетов npm вне разрешённых (разрешительный список фабрики или `licenses` в `.factory/config.yml` цели). Замечания - только к новому; шаг сканеров - на своём раннере, без ключей.
- Доставка: задача агента (метка `agent-review`) закрывается сама, когда выложенный на стенд коммит ветки по умолчанию содержит её ключ, - комментарий со ссылками на коммит, PR и выкладку, сообщение в `#разработка`. Баги сбоев закрывает проход сбоев.
- Спецификация задачи агента - изменение OpenSpec, утверждённое слиянием PR: каталог `openspec/changes/<ключ в нижнем регистре>-<имя>/` ветки по умолчанию (например `draw-12-redraw-unclaimed-prize`). Фабрика отдаёт его артефакты (замысел, дизайн, задачи, план проверки, требования со сценариями) агенту в задании и пишет в вердикте стража, было ли изменение.
- Тест до кода (шаг агента, `factory-test-first`): модульные тесты изменения гоняются на коде базы (код изменения снят) и с изменением, команда - `checks.test` цели. Тесты падали на базе и проходят с изменением - сведение в вердикте; код без модульных тестов, тесты, что проходят и без кода, и тесты, что падают с изменением, - замечания (решает человек).
- Шаблоны вывода фабрики (`images/coordinator/templates.ts`): модель отдаёт данные по схеме, текст собирает код - одна форма в похожих случаях. Задача нарезки: цель, сценарии приёмки (Дано, Когда, Тогда), вне рамок, основания, откуда; ответ библиотекаря: коротко, подробнее, источники. По схеме и шаблону уже работали вердикты стража и сканеров, судьи PR и макета, отказы реестра ролей, заметки о выпуске, баг сбоя и доставка. Спецификации цели - стандарт OpenSpec (схема фабрики), навыки - Agent Skills.
- ИИ-персонажи для видео-демо: у каждого своя учётка бота Discord и запись держателя вида `ai` в реестре ролей цели; бот фабрики слышит чужого бота, только если тот держатель ролей, и проверяет его права по роли. Завести бота - мастер `scripts/persona-bot-add.sh ПЕРСОНАЖ "ИМЯ" РОЛЬ` (учётку создаёт человек на портале Discord, токен - в `.state/discord-ПЕРСОНАЖ.env`); реплика - `scripts/persona.sh ПЕРСОНАЖ КАНАЛ ТЕКСТ`.
- Съёмка видео-демо (`scripts/demo-film.sh`): режиссёр идёт по сценарию съёмки `docs/demo/film.yml` - участники действуют через API под своими учётками (бот Discord у ИИ-персонажа, учётка Atlassian у человека), итог шага ждётся по наблюдаемому признаку, камера (Playwright 1.63 без окна, образ `factory/camera`) снимает экран браузера участника с его плашкой и карточкой главы. Вход камеры в Atlassian - `.state/camera/jira.json`; клипы и манифест - `.state/films/<время>/`. Discord в кадр не входит: его снимают записью окна (OBS).
- Источник `bitbucket-pipelines.yml` - `config/bitbucket/`; в Bitbucket его кладёт `scripts/bb-commit.sh`.

## Проверка

После "положил" фабрика проверяет только наличие файлов и делает пробные запросы на чтение (кто я, доступ к проекту, к репозиторию, к серверу), значения не печатаются.
