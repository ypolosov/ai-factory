# ai-factory

Шаблон открытой self-hosted фабрики ПО на ИИ: задача -> агент в песочнице -> PR -> проверки -> слияние человеком -> выкладка -> эксплуатация -> новые задачи. Фабрика как код: compose, настройки, скрипты. Только компоненты под лицензиями OSI.

**Статус:** стенд, этап 6 из 10. Работают git-хостинг Forgejo, три runner (агент, проверки, выкладка), шлюз моделей, путь "задача с меткой agent -> агент -> PR от бота" для OpenCode, Claude Code и Codex, проверки PR (тесты, секреты, зависимости, статический анализ, ревью ИИ), выкладка на стенд с откатом, закрытая сеть заданий и проверки доступности, которые сами заводят задачи о сбоях.

## Быстрый старт

Нужны Docker с Compose, `curl`, `jq`, `git`.

```sh
./scripts/stand-up.sh       # Forgejo, учётки, три runner, шлюз; повторный запуск безопасен
./scripts/smoke.sh          # пустышка с заданием на каждом runner должна пройти
./scripts/gateway-check.sh  # ключи шлюза, ограничения по моделям, открытая модель, учёт по задаче
./scripts/setup-repo.sh hello   # репозиторий из examples/hello: бот, защита main, метка agent, секреты
./scripts/new-task.sh hello "Приветствие hello world" examples/tasks/hello-world.md  # задача -> PR -> проверки
./scripts/setup-repo.sh todo    # репозиторий из examples/todo: OpenSpec, роли агентов, метки ролей
./scripts/new-task.sh todo "Спецификация: todo list" examples/tasks/todo-spec.md agent:spec  # спецификация -> PR
```

Forgejo: http://127.0.0.1:3000, вход `factory-admin`, пароль - в `.state/admin.password`.

Проверки репозитория: `make check` (shellcheck, shfmt, `docker compose config`).

## Шлюз моделей

Адрес: http://127.0.0.1:4000 (OpenAI Chat и Responses, Anthropic Messages). Клиент предъявляет ключ шлюза в заголовке `x-gateway-key` и помечает задачу заголовком `x-task-id`: по нему в журнале шлюза (`.state/gateway-db/`, SQLite) копятся токены и цена.

Три ключа в `.state/`:

| Ключ | Модели | Бюджет |
|---|---|---|
| `gw-agent-api.key` | открытые: `default` (GLM-5.3-Flash), `hard` (GLM-5.3), `alt` (DeepSeek-V4.1-Flash) через OpenRouter | `GATEWAY_AGENT_DAILY_USD` в сутки, по умолчанию 2 доллара |
| `gw-agent-sub.key` | `claude-*` и `gpt-*` по подпискам владельца | без денежного бюджета: подписка с фиксированной ценой, шлюз пишет теневую цену |
| `gw-owner.key` | все | без бюджета |

Ключ провайдера открытых моделей кладётся так, чтобы не попасть в историю терминала, после чего шлюз перезапускается:

```sh
read -rs KEY && printf %s "$KEY" > .state/gateway/openrouter.key && unset KEY
docker compose restart gateway
```

Подписки (проверка вручную, нужны входы владельца на этой машине):

```sh
# Claude Code: вход по подписке остаётся, запросы идут через шлюз
ANTHROPIC_BASE_URL=http://127.0.0.1:4000 \
ANTHROPIC_CUSTOM_HEADERS="$(printf 'x-gateway-key: %s\nx-task-id: manual-1' "$(cat .state/gw-agent-sub.key)")" \
claude -p "Ответь одним словом: ok" --model claude-haiku-4-5

# Codex: свой провайдер со входом ChatGPT (встроенный openai переопределить нельзя)
codex exec --skip-git-repo-check -s read-only -c model_provider=gw \
  -c "model_providers.gw={name=\"gateway\",base_url=\"http://127.0.0.1:4000/v1\",wire_api=\"responses\",requires_openai_auth=true,http_headers={\"x-gateway-key\"=\"$(cat .state/gw-agent-sub.key)\",\"x-task-id\"=\"manual-2\"}}" \
  "Ответь одним словом: ok"
```

## Роли агентов и спецификации

Метка на задаче выбирает роль агента: `agent` - разработка, `agent:spec` - спецификация, `agent:tests` - приёмочные тесты. Исполнитель, модель и разрешённые пути роли берутся из `.factory/config.yml` основной ветки репозитория (шаблон - `examples/todo`); без файла - из переменных репозитория `FACTORY_EXECUTOR` и `FACTORY_MODEL`. Ворота публикации отклоняют патч, который меняет пути вне правил роли: спецификация меняет только `openspec/`, тестировщик - только `tests/acceptance/`, разработчик - всё, кроме `.forgejo/`, `.github/`, `.factory/`, `openspec/` и `tests/acceptance/`. Сам файл настроек не может поменять ни одна роль.

Задачи из спецификации: после слияния изменения OpenSpec в main workflow `tasks.yml` заводит задачу Forgejo на каждый пункт `tasks.md` с зависимостями между ними (`factory-tasks`); метку роли ставит человек. Проект todo - на TypeScript (Node 24 стирает типы, без сборки), приёмочные сценарии - Gherkin в `features/` с метками пунктов `@task-X.Y`.

Доработка: метку роли на задаче снимают и ставят заново (`scripts/rework.sh РЕПОЗИТОРИЙ НОМЕР`; ставить метки могут только участники с правом записи). Если у задачи уже есть ветка `agent/issue-N`, агент продолжает в ней и получает в задаче замечания к прошлой попытке: комментарии и ревью PR после её последнего коммита - ревью ИИ и замечания человека (`factory-feedback`). Публикация добавляет коммит поверх ветки, PR обновляется.

Спецификации - OpenSpec 1.13.2 (MIT): живые требования в `openspec/specs/`, изменения - в `openspec/changes/<имя>/` по схеме фабрики `openspec/schemas/factory`: замысел, требования со сценариями, архитектурные решения (ADR), задачи, план проверки. Навыки OpenSpec лежат в `.agents/skills` (Codex, OpenCode) и `.claude/skills` (Claude Code); правила для агентов - один файл `AGENTS.md`. Почему OpenSpec, а не Spec Kit, BMAD или Superpowers: формат не зависит от обвязки, спецификация живёт вместе с кодом, CLI отдаёт задачи в JSON.

## Задача -> PR

Метка `agent` на задаче запускает `.forgejo/workflows/agent.yml` целевого репозитория (шаблон - `examples/hello`):

1. `implement` (runner агента): рабочая копия, текст задачи как недоверенный ввод (через переменные окружения и файл, не подстановкой в команду), `factory-agent` запускает выбранную обвязку. У агента есть ключ шлюза своей роли и нет права записи в git. Патч, `run.json` и журнал уходят артефактом.
2. `publish` (runner проверок): ключа модели нет, токен бота есть. `factory-publish` отклоняет пустой патч, правки `.forgejo/` и `.github/` (и переименования туда), патч больше 3000 строк или 1 МБ; иначе - ветка `agent/issue-N` и PR "Closes #N".
3. PR запускает `ci.yml` - проверки PR (ниже). Ветку `main` пишет и сливает только человек и только при зелёных обязательных проверках.

Контракт исполнителя (`images/agent/factory-agent`): вход - рабочая копия, текст задачи, `FACTORY_EXECUTOR` (`opencode`, `claude`, `codex`), `FACTORY_MODEL`, адрес и ключ шлюза, номер задачи для учёта; выход - `agent.patch`, `run.json`, `agent.log` и код возврата. Исполнитель и модель - переменные репозитория: `setup-repo.sh ИМЯ [исполнитель] [модель]`. Повторный запуск `setup-repo.sh` приводит `.forgejo/` репозитория к шаблону, код проекта не трогает.

Недоверенный код - обвязка агента и тесты из PR - работает через `factory-untrusted`: от пользователя `node` и только с переменными окружения из списка. По документации Forgejo каждый шаг задания получает автоматический токен задания (`FORGEJO_TOKEN`, `GITHUB_TOKEN`); недоверенному коду он не достаётся, фоновые процессы недоверенного кода завершаются вместе с ним.

### Проверки PR

| Статус | Что проверяет | Чем | Обязательна |
|---|---|---|---|
| `ci / test` | тесты проекта; код из PR - недоверенный (`factory-untrusted`) | `node --test`: команда задана в workflow, сценарий `package.json` её не подменит | да |
| `ci / secrets` | секреты в коммитах PR | Gitleaks 8.30.1 | да |
| `ci / deps` | уязвимые зависимости по файлам блокировки | OSV-Scanner 2.6.0 (база osv.dev) | да |
| `ci / sast` | опасные конструкции кода | Opengrep 1.30.1 и правила фабрики `images/agent/checks/opengrep.yml` | да |
| `ci / types` | типы TypeScript (todo) | `tsc --noEmit`, TypeScript 7.0.2 из `devDependencies` | да |
| `ci / acceptance` | приёмочные сценарии Gherkin (todo): все - сухой прогон, по-настоящему - `@always`, сделанные пункты и пункт PR | cucumber-js 13.2.1, `factory-acceptance` | да |
| `ci / mutation` | сила модульных тестов на изменённом коде `src/` (todo) | StrykerJS 10.0.0 с настройками фабрики, порог `gate.mutation_break` | да |
| `ci / gate` | ворота ИИ для PR агента-разработчика (todo): оценка судьями и решение | `factory-gate` в образе ревьюера (ниже) | да |
| `ci / review` | ревью ИИ комментарием в PR, совет человеку | PR-Agent 0.46.0, модель `hard`, запасная `alt` | нет |

Сканеры берут настройки фабрики из `/etc/factory/checks` и не слушают то, чем PR мог бы ослабить проверку: `.gitleaks.toml`, `.gitleaksignore` и пометки `gitleaks:allow`, `osv-scanner.toml`, `.semgrepignore` и пометки `nosemgrep`. Каталоги `test/` статический анализ тоже проверяет. Проверено тестовым PR с поддельным токеном, уязвимой зависимостью и `eval`, каждый с такой уловкой: все три проверки красные.

Правила статического анализа свои (Apache-2.0): наборы сообщества semgrep-rules и opengrep-rules идут с условием Commons Clause и требованию "только лицензии OSI" не отвечают. Тесты правил: `opengrep scan --test /etc/factory/checks` в образе исполнителя. Trivy (образы, IaC) - на этапе выкладки, когда появится образ приложения.

### Ворота ИИ и круг доработки

Для PR агента-разработчика (todo) задание `gate` после детерминированных проверок зовёт судей - модели шлюза из семейств, отличных от модели разработки (`roles.review.models` и `families` в `.factory/config.yml`; сейчас DeepSeek и Qwen против GLM). Судья - PR-Agent в режиме простого диффа (без описания PR и настроек из ветки) с баллом 0-100 и задачей из трекера как контекстом. Решение (`gate` в `.factory/config.yml`):

- красные проверки, балл ниже `rework_below` (60) или `changes_required` - находки комментарием в PR и повторная метка задачи: агент дорабатывает в той же ветке; не больше `max_iterations` (3) кругов;
- замечания по безопасности, разброс баллов больше `max_spread`, середина шкалы, нет балла, круги исчерпаны - метка `ai:needs-human`;
- балл от `human_from` (80) - метка `ai:ready-for-human`.

Агенту уходят находки и красные проверки, но не балл: он - в статусе коммита `factory / ai-gate` для человека. Образ ревьюера `factory/reviewer:stand` (PR-Agent, jq, yq, `factory-gate`) стенд собирает на хосте.

### Подписки владельца в заданиях

Claude Code и Codex работают в заданиях по подпискам владельца, запросы идут через шлюз с ключом `gw-agent-sub`. Входы кладутся в `.state/` так, чтобы не попасть в историю терминала:

```sh
# Claude Code: долгоживущий токен подписки (не API-ключ: расходует лимиты плана)
claude setup-token
read -rs T && printf %s "$T" > .state/claude-oauth.token && unset T

# Codex: отдельный вход ChatGPT для фабрики, не общий со входом на этой машине
mkdir -p -m 700 .state/codex
CODEX_HOME=$PWD/.state/codex codex login    # без браузера: --device-auth
```

`setup-repo.sh ИМЯ claude` или `setup-repo.sh ИМЯ codex` кладёт вход в секрет репозитория; задание отдаёт его только выбранному исполнителю. Если Codex обновит токены внутри задания, в журнале задания появится предупреждение: вход фабрики мог устареть - войти заново и снова запустить `setup-repo.sh`. Своя песочница Codex (bubblewrap) в контейнере задания не запускает команд, поэтому Codex работает с `--sandbox danger-full-access`: песочница - контейнер задания и пользователь `node`.

## Выкладка

Служба выкладки (`deployer`) раз в 15 секунд смотрит main приложений из `DEPLOY_APPS` (`владелец/репозиторий=порт`) и выкладывает новый коммит:

1. собирает образ по рецепту фабрики (`images/deployer/recipes/node.Dockerfile`: код из `src/`, запуск `node src/server.js`); шаги сборки задаёт фабрика, а не репозиторий;
2. проверяет образ Trivy: уязвимости HIGH и CRITICAL, у которых есть исправление, не пускают на стенд;
3. поднимает его проектом compose на Docker стенда (`deploy-dind`, порты `127.0.0.1:8080-8089`) и проверяет `GET /health`; не поднялся - возвращает прежнюю версию;
4. пишет на коммит статус `deploy / stand` со ссылкой на стенд.

Теги образов - `приложение:первые-12-знаков-коммита`.

```sh
./scripts/rollback.sh hello status              # что на стенде сейчас и что было до этого
./scripts/rollback.sh hello                     # вернуть прошлую версию
./scripts/rollback.sh hello hello:a0b4f12c1f65  # вернуть указанную
./scripts/deploy.sh hello [SHA]                 # выложить вручную (обычно не нужно)
```

Задания Actions доступа к Docker не получают: выкладывает только служба. Это модель "забирает сама", как у Argo CD и Flux, на которые фабрика перейдёт в Kubernetes. Реестр образов пока не нужен: образы живут в Docker стенда.

## Эксплуатация

Gatus (Apache-2.0) раз в 15 секунд проверяет `GET /health` приложения стенда (первое из `DEPLOY_APPS`) и раз в 30 секунд - Forgejo. Три неудачи подряд - Gatus сам заводит в репозитории приложения задачу `alert(gatus): стенд/<приложение>` от учётки `factory-ops`; две удачи подряд - закрывает её. Задача приходит без метки `agent`: брать ли её агенту, решает человек. Страница проверок - http://127.0.0.1:8100, сами проверки - `config/gatus/config.yaml.tmpl`.

Проверено: приложение на стенде остановлено - задача заведена через 24 с; приложение снова отвечает - задача закрыта через 24 с.

## Сеть заданий

Docker заданий агента и проверок (`agent-dind`, `ci-dind`) живёт во внутренней сети `jobs` без выхода в интернет. Напрямую видны только Forgejo и шлюз моделей. Наружу - через прокси `egress` и только по списку `images/egress/allowlist.txt`: npm, OSV, вход Codex. Прокси задан заданиям в настройках runner. Образы заданий стенд собирает и скачивает на хосте и загружает в Docker заданий сам (`scripts/stand-up.sh`).

Отказы прокси видны в `docker compose logs egress` (строки `TCP_DENIED`). Проверено: прямой выход из задания в интернет не проходит, неразрешённые адреса через прокси получают отказ, все три исполнителя и проверки PR работают.

## Решения безопасности

- порты Forgejo и шлюза публикуются только на `127.0.0.1`;
- Docker API каждого dind - только unix-сокет в общем томе с его runner; контейнеры заданий его не видят (`docker_host: "-"`), по сети dockerd не слушает;
- общий кэш Actions выключен; задания запускаются без privileged;
- ключ провайдера знает только шлюз; в настройках шлюза лежат хэши ключей, а не ключи;
- секреты - в `.state/` (в git не попадает), в командную строку не передаются;
- в контейнеры монтируются каталоги, а не одиночные файлы: Docker Desktop теряет смонтированный файл, если его заменить;
- агент и тесты из PR работают от непривилегированного пользователя без токена задания; токен записи есть только у задания публикации, а у него нет ключа модели;
- `main` защищена: бот не пишет в неё и не сливает PR;
- задания агента и проверок не выходят в интернет мимо прокси со списком адресов;
- выкладывает служба фабрики по рецепту фабрики; задания Docker не получают.

## Что ещё не закрыто

- через разрешённые адреса (например, публикацией пакета в npm) данные всё ещё можно вынести: список защищает от простого выноса, не от целенаправленного; следующий шаг - свой прокси npm только на чтение;
- Docker стенда и задания выкладки выходят в интернет напрямую: там работает только слитый человеком код;
- переключение версии на стенде идёт с простоем в несколько секунд (без сине-зелёной выкладки);
- ошибки приложения в задачи пока не попадают: GlitchTip не подключён; Gatus следит только за первым приложением из `DEPLOY_APPS`;
- агент может ослабить сами тесты (удалить, пропустить, упростить); это видят ревью ИИ и человек, автоматической проверки нет;
- ревью ИИ цитирует код из PR, в том числе найденный секрет;
- для моделей Codex в каталоге шлюза нет теневой цены: учёт по задаче - только в токенах.
